[지난 글](/posts/optimistic-ui-instagram-likes/)에서는 인스타그램의 좋아요를 예로 들어 낙관적 UI를 정리했다.

사용자의 행동을 화면에 먼저 반영하고, 서버의 처리 결과는 나중에 확인하는 방식이었다.

채팅도 비슷하게 생각할 수 있다.

메시지를 보내면 말풍선을 먼저 보여주고, 서버에서 응답이 오면 전송 상태를 바꾸는 것이다.

그런데 여기서 질문이 생긴다.

**서버에서 도착한 메시지가 이미 화면에 보여준 그 메시지라는 것을 어떻게 알 수 있을까?**

그냥 새로 추가하면 같은 메시지가 두 번 나타날 수 있다.

도착하는 순서대로 붙이면 대화 순서가 어색해질 수도 있다.

인터넷이 끊겨 응답을 받지 못했다면, 메시지를 다시 보내도 되는지도 고민해야 한다.

말풍선을 먼저 띄우는 것까지는 단순해 보였는데, 그다음부터 생각할 일이 많아진다.

## 숨숨파인더에서 했던 고민

예전에 숨숨파인더 프로젝트에서는 WebSocket과 Kafka를 사용했다.

당시 나는 Data와 백엔드 파트를 담당했고, 채팅 기능을 직접 맡지는 않았다.

다만 응답을 기다려 채팅을 화면에 반영하는 과정에서, 보낸 메시지와 받은 메시지의 표시 순서가 조금 어긋나는 상황이 있었던 것은 기억한다.

그래서 이런 방향을 제안했었다.

“내가 보낸 메시지는 화면에 먼저 보여주고, 서버에서 데이터가 오면 확인해서 상태를 맞추면 어떨까?”

세부적인 처리 방식이나 최종 구현까지는 정확히 기억나지 않는다.

따라서 이 글은 당시 구현을 복원하거나 원인을 분석한 회고는 아니다.

**그때 했던 고민을 지금 다시 설계해본다면 무엇이 필요할지 정리한 글이다.**

메시지 하나를 작성해서 서버의 저장을 확인할 때까지 따라가보려고 한다.

---

## 먼저 보여준 메시지에도 이름이 필요하다

다음 메시지를 보낸다고 가정해보자.

```text
안녕하세요. 내일 오후에도 가능할까요?
```

낙관적 UI를 적용하면 서버 응답을 기다리지 않고 화면에 표시할 수 있다.

```text
안녕하세요. 내일 오후에도 가능할까요?

전송 중…
```

그런데 아직 서버에 저장되기 전이라면 서버가 부여하는 메시지 ID도 없을 수 있다.

나중에 응답이 왔을 때 어떤 말풍선의 상태를 바꿔야 할까?

내용으로 찾으면 될까?

같은 사람이 “네”를 두 번 보낼 수도 있다. 내용이 같다고 같은 메시지는 아니다.

그래서 지금 설계한다면 **클라이언트에서 메시지를 작성할 때 고유한 ID를 먼저 만들 것 같다.**

```json
{
  "clientMessageId": "client-msg-a1",
  "roomId": "room-123",
  "content": "안녕하세요. 내일 오후에도 가능할까요?"
}
```

`clientMessageId`는 설명을 위한 필드 이름이다.

중요한 것은 이름보다 역할이다.

**서버에 저장되기 전부터 이 메시지를 다른 메시지와 구분할 수 있어야 한다.**

이 ID를 화면에 표시하는 메시지와 전송 요청에 함께 넣는다.

---

## 서버 응답이 오면 말풍선을 하나 더 만드는 게 아니다

서버가 메시지를 저장한 뒤 다음과 같은 응답을 준다고 가정해보자.

```json
{
  "clientMessageId": "client-msg-a1",
  "messageId": "server-msg-9812",
  "roomSequence": 152,
  "status": "stored"
}
```

각 필드는 다음 역할을 한다.

| 필드 | 역할 |
|---|---|
| `clientMessageId` | 클라이언트가 먼저 표시한 메시지를 찾는 기준 |
| `messageId` | 서버에 저장된 메시지를 식별하는 기준 |
| `roomSequence` | 서버가 정한 채팅방 내 메시지 순서 |
| `status` | 서버에서 확인된 처리 상태 |

클라이언트는 응답의 `clientMessageId`로 기존 말풍선을 찾는다.

그리고 서버 메시지 ID와 순서 정보를 연결하고, 전송 상태를 바꾼다.

```text
기존 메시지 찾기
→ 서버 정보 반영
→ 전송 중 표시 해제
```

**응답을 받았다고 같은 내용을 채팅 목록에 한 번 더 추가하는 것이 아니다.**

이 부분은 내 메시지가 실시간 이벤트로 다시 들어오는 구조에서도 중요하다.

예를 들어 서버가 발신자에게 저장 결과를 응답하면서, 채팅방 참여자들에게도 새 메시지 이벤트를 전달할 수 있다.

그렇다면 내 화면에서는 하나의 메시지가 여러 경로로 들어올 수 있다.

이때도 메시지 ID를 기준으로 기존 항목에 합쳐야 한다. 실시간 이벤트가 먼저 도착하고 응답이 나중에 와도 결과는 같아야 한다.

이미 저장을 확인한 메시지를 뒤늦은 타임아웃 때문에 다시 실패 상태로 바꾸지 않는 것도 필요하다.

여기서 `stored`는 **서버가 메시지를 저장했다는 의미**로 정한 것이다.

요청을 받았다는 확인인지, 저장이 끝났다는 확인인지 프론트와 백엔드가 합의해야 한다. 상대방의 수신이나 읽음은 별도로 다룬다.

## 같은 메시지인지는 알겠는데, 순서는 어떻게 하지?

여기까지는 메시지를 구분하는 이야기였다.

하지만 같은 메시지를 알아보는 것과 대화 순서를 정하는 것은 다른 문제다.

예를 들어 내가 A를 보낸 직후 상대방의 B가 도착했다고 해보자.

내 화면에는 이미 A가 있다.

```text
A: 내 메시지 — 전송 중
B: 상대방 메시지
```

그런데 서버에서는 B가 먼저 처리되고 A가 나중에 처리됐을 수도 있다.

그러면 무엇을 기준으로 정렬해야 할까?

내가 화면에서 먼저 봤던 순서일까?

각 휴대폰에서 메시지를 작성한 시간일까?

서버에서 확정한 순서일까?

여기에는 서비스 차원의 기준이 필요하다.

지금 예시에서는 **서버가 채팅방 안에서 확정한 순서**를 기준으로 삼아보려고 한다.

```text
roomSequence 151 → B
roomSequence 152 → A
```

각 기기의 시계가 정확히 같다고 가정하기 어렵고, 서로 다른 사용자가 작성한 시각만으로 모두가 공유할 순서를 정하기도 까다롭기 때문이다.

물론 `roomSequence`라는 필드를 추가한다고 순서가 저절로 만들어지는 것은 아니다.

서버에서 같은 채팅방의 순서를 일관되게 부여하는 방법이 필요하다. 이 값은 사용자가 실제로 타이핑한 절대적인 시간순서를 알아내는 장치도 아니다. **서비스가 합의한 순서를 표현하는 값**이다.

아직 서버 순서가 없는 내 메시지는 임시로 표시할 수 있다. 다만 확정 후 위치가 달라질 수 있으므로, 전송 대기 메시지를 어떻게 배치하고 이동을 보여줄지도 정해야 한다.

**낙관적 UI는 입력에 대한 반응을 빠르게 만든다. 대화의 최종 정렬 기준까지 대신 정해주지는 않는다.**

### Kafka를 쓰면 순서는 보장되는 것 아닐까?

이 부분도 범위를 나눠서 봐야 한다.

Kafka가 제공하는 순서 보장은 기본적으로 **같은 파티션 안에 기록된 이벤트의 순서**에 관한 것이다. 공식 문서에서도 소비자는 해당 파티션의 이벤트를 기록된 순서대로 읽는다고 설명한다.

출처: [Apache Kafka — Introduction](https://kafka.apache.org/intro/)

그래서 Kafka를 쓴다는 사실만으로 채팅 화면의 최종 표시 순서까지 결정되지는 않는다.

파티션에 기록된 순서, 애플리케이션이 처리를 끝낸 순서, 클라이언트가 화면을 갱신하는 방식은 함께 살펴봐야 한다.

이것이 당시 숨숨파인더 문제의 원인이었다는 뜻은 아니다.

다시 확인한다면 **어느 단계의 순서를 이야기하고 있는지부터 구분해야겠다**는 의미다.

## 인터넷이 끊기면 메시지는 어디에 남아 있을까?

순서를 생각하다 보면 연결이 끊기는 상황도 만나게 된다.

사용자가 메시지를 보냈는데 인터넷이 잠깐 끊겼다고 해보자.

화면에는 말풍선이 있다.

그런데 서버에는 아직 전달되지 않았을 수 있다.

이때 화면 상태에만 메시지를 넣어뒀다면 앱을 종료했을 때 사라질 수도 있다.

“연결되면 다시 보내자”를 실제로 구현하려면, 다시 보낼 내용을 보관해야 한다.

이런 공간을 **발신 대기함, Outbox**처럼 생각할 수 있다.

여기서는 클라이언트 기기에 두는 발신 대기함을 뜻한다.

```text
메시지 작성
→ 메시지와 ID를 기기에 저장
→ 화면에 전송 대기로 표시
→ 연결이 가능하면 전송 시도
→ 서버 저장 확인
→ 발신 대기 작업 완료
```

앱을 다시 켜도 이어서 보낼 수 있어야 한다면, 메모리뿐 아니라 기기의 지속적인 저장소가 필요하다.

Socket.IO 문서에서도 클라이언트 재시도를 설정하더라도 탭을 새로고침하면 대기 중인 이벤트가 사라질 수 있다고 설명한다. 통신 라이브러리의 버퍼와 앱이 관리하는 지속적인 발신 대기함은 구분해야 한다.

참고: [Socket.IO — Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

여기서 Socket.IO는 전달 보장을 설명하기 위한 참고 사례다. 숨숨파인더에서 사용한 WebSocket 구현체가 Socket.IO였다는 의미는 아니다.

## 그런데 서버에는 이미 저장됐을 수도 있다

전송이 안 됐으면 다시 보내면 될 것 같다.

그런데 조금 애매한 상황이 있다.

```text
클라이언트 → 서버: 메시지 전송

서버: 저장 완료

서버 → 클라이언트: 성공 응답
                 ✕ 연결 끊김
```

메시지는 저장됐다.

하지만 클라이언트는 응답을 받지 못했다.

이때 클라이언트가 알 수 있는 것은 “성공 응답을 확인하지 못했다”는 사실이다.

**서버가 저장하지 않았다는 사실까지 알 수 있는 것은 아니다.**

그래서 무작정 다시 보내면 같은 메시지가 두 번 저장될 수 있다.

이때 앞에서 만든 `clientMessageId`를 다시 활용할 수 있다.

처음 보낼 때도 `client-msg-a1`.

같은 메시지를 재전송할 때도 `client-msg-a1`.

서버는 인증된 발신자와 이 ID를 기준으로 이미 처리한 요청인지 확인한다. 이미 저장했다면 새 메시지를 만들지 않고 기존 저장 결과를 반환하도록 설계할 수 있다.

이렇게 같은 요청을 반복해도 메시지가 추가로 생성되지 않도록 만드는 것이 이 사례에서의 **멱등성**이다.

AWS의 설명에서도 클라이언트 요청 ID를 이용해 재시도를 식별하고, 이미 처리한 요청에는 의미상 같은 결과를 반환하는 방식을 다룬다.

출처: [AWS Builders’ Library — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

주의할 부분은 두 가지다.

재시도할 때마다 새로운 ID를 만들면 서버는 새로운 메시지로 볼 수 있다.

또한 “이미 있는지 조회한 다음 저장”하는 것만으로는 동시에 들어오는 중복 요청을 막기 어렵다. 고유 제약과 트랜잭션 등을 이용해 중복 판정과 저장이 안전하게 이루어지도록 해야 한다.

클라이언트는 같은 메시지를 다시 보낸다는 사실을 유지하고, 서버는 그 요청을 여러 번 받아도 중복 생성하지 않도록 약속하는 것이다.

---

## 계속 보내기만 하면 되는 것은 아니다

인터넷이 잠깐 끊긴 경우라면 재시도가 도움이 될 수 있다.

하지만 채팅방이 삭제됐거나 메시지를 보낼 권한이 없어진 경우라면 어떨까?

같은 요청을 계속 보내도 해결되지 않는다.

그래서 상태를 조금 더 나눠두는 편이 좋겠다.

| 상태 | 화면에서 전달할 의미 |
|---|---|
| 전송 대기 | 보낼 내용을 보관했고 전송 기회를 기다리는 중 |
| 전송 중 | 요청을 보냈지만 저장 확인을 아직 받지 못함 |
| 전송 완료 | 서버 저장을 확인함 |
| 확인 필요 | 결과가 불확실하거나 자동 재시도를 멈춰 사용자 조치가 필요함 |
| 전송 거부 | 권한 등으로 서버가 요청을 명확하게 거부함 |

이 상태 이름도 하나의 설계 예시다.

중요한 것은 타임아웃과 명확한 거부를 똑같이 취급하지 않는 것이다.

일시적인 통신 문제에는 간격을 늘리며 제한적으로 재시도할 수 있다. 계속 확인되지 않으면 사용자가 다시 시도하거나 내용을 복사할 수 있도록 남겨둘 수 있다.

실패했다고 사용자가 작성한 메시지를 바로 지워버리고 싶지는 않다.

그리고 연결이 복구됐을 때는 내 발신 대기함만 확인해서도 안 된다.

**연결이 끊긴 동안 상대방이 보낸 메시지도 다시 받아와야 한다.**

마지막으로 동기화를 마친 위치를 기준으로 누락 구간을 조회하고, 이미 화면에 있는 메시지는 ID로 합치는 방식 등을 생각할 수 있다. Socket.IO 문서도 이벤트 ID와 마지막 수신 위치를 이용한 재연결 시 복구 방식을 예시로 설명한다.

참고: [Socket.IO — Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

연결이 다시 열리는 것과 대화 내용이 다시 맞춰지는 것은 각각 확인해야 할 일이다.

## 말풍선 하나에 생각보다 많은 약속이 들어 있었다

처음에는 이런 생각이었다.

“메시지를 먼저 보여주고, 서버에서 응답이 오면 바꾸면 되지 않을까?”

그런데 그 한 문장 안에는 여러 약속이 필요했다.

먼저 보여준 메시지를 어떻게 찾을 것인가.

응답과 실시간 이벤트가 모두 오면 어떻게 합칠 것인가.

어떤 기준으로 대화를 정렬할 것인가.

연결이 끊기면 무엇을 보관하고 언제 다시 보낼 것인가.

응답만 사라졌을 때 중복 저장을 어떻게 막을 것인가.

숨숨파인더에서 했던 제안을 지금 다시 꺼낸다면, 말풍선을 먼저 표시하자는 이야기와 함께 **메시지 ID, 저장 확인의 의미, 정렬 기준**부터 정할 것 같다.

프론트에서는 사용자에게 현재 상태를 보여주고, 백엔드에서는 그 상태를 확정할 수 있는 정보를 제공해야 한다.

그 약속이 있어야 먼저 띄운 말풍선이 실제 대화 기록으로 이어질 수 있다.
