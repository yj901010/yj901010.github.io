인기글 목록을 보다 보면 가끔 이런 생각이 들 때가 있다.

“이 글 아까 위에서 본 것 같은데?”

읽었던 글의 제목이 회색으로 표시돼 있다면 더 알아보기 쉽다.

분명 아까 읽은 글인데, 목록을 더 내려보다가 다시 만난다. 새로고침했더니 글들의 순서가 바뀌어 있기도 하다.

인기순이니까 순위가 바뀌는 것은 자연스럽다.

그런데 개발하는 입장에서 생각해보면 한 가지 궁금해진다.

**마지막으로 본 글 다음부터 가져오도록 만들었는데도, 같은 글이 다시 나올 수 있을까?**

서비스마다 구현은 다르겠지만, 좋아요 수를 기준으로 커서 페이징을 한다고 가정하면 이런 상황을 생각해볼 수 있다.

## 최신순에서는 기준이 잘 바뀌지 않는다

최신순 목록에서는 마지막으로 본 글의 생성 시각과 ID를 커서에 담아둘 수 있다.

생성 시각이 같은 글도 있을 수 있으니, 고유한 ID를 함께 사용해 순서를 정한다.

```sql
SELECT id, title, created_at
FROM posts
WHERE created_at < :last_created_at
   OR (
       created_at = :last_created_at
       AND id < :last_id
   )
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

마지막으로 본 글보다 오래된 글을 가져온다.

생성 시각이 같다면 ID가 더 작은 글을 가져온다.

여기서 중요한 전제는 **기존 글의 생성 시각과 ID가 바뀌지 않는다는 것**이다.

새 글이 목록 위에 추가돼도, 기존 글들이 정렬값 변경 때문에 커서의 앞뒤를 오가지는 않는다.

그럼 인기순에서는 생성 시각 대신 좋아요 수를 사용하면 될까?

## 인기순도 쿼리는 비슷하다

여기서는 좋아요가 많은 글일수록 인기 있는 글이라고 가정해보자.

좋아요 수가 같으면 ID가 큰 글을 먼저 보여준다. `like_count`에는 `NULL`이 없고, ID는 고유하며 바뀌지 않는다고 가정한다.

첫 목록은 다음처럼 가져올 수 있다.

```sql
SELECT id, title, like_count
FROM posts
ORDER BY like_count DESC, id DESC
LIMIT 2;
```

데이터가 다음과 같다면 A와 B를 가져오게 된다.

| 글 | ID | 좋아요 수 |
|---|---:|---:|
| A | 105 | 100 |
| B | 104 | 90 |
| C | 103 | 80 |
| D | 102 | 70 |

마지막으로 가져온 글은 B다.

따라서 다음 조회를 위한 커서에는 B의 당시 좋아요 수와 ID를 담는다.

```json
{
  "likeCount": 90,
  "id": 104
}
```

다음 목록을 가져오는 쿼리는 이렇게 된다.

```sql
SELECT id, title, like_count
FROM posts
WHERE like_count < 90
   OR (
       like_count = 90
       AND id < 104
   )
ORDER BY like_count DESC, id DESC
LIMIT 2;
```

좋아요가 90개보다 적거나, 90개로 같으면서 ID가 104보다 작은 글을 가져온다.

데이터가 그대로라면 결과는 예상한 대로다.

```text
첫 조회: A, B
다음 조회: C, D
```

여기까지만 보면 최신순과 크게 다르지 않다.

## 그런데 다음 조회 전에 좋아요 수가 바뀐다면?

A와 B를 본 뒤, 다음 목록을 불러오기 전에 A의 좋아요가 취소되어 75개로 줄었다고 해보자.

```sql
-- 상황을 단순화한 예시
UPDATE posts
SET like_count = 75
WHERE id = 105;
```

현재 인기순 목록은 이렇게 바뀐다.

| 글 | ID | 좋아요 수 |
|---|---:|---:|
| B | 104 | 90 |
| C | 103 | 80 |
| A | 105 | 75 |
| D | 102 | 70 |

클라이언트가 기억하고 있는 커서는 여전히 `(90, 104)`다.

같은 다음 목록 쿼리를 실행하면 어떻게 될까?

```sql
SELECT id, title, like_count
FROM posts
WHERE like_count < 90
   OR (
       like_count = 90
       AND id < 104
   )
ORDER BY like_count DESC, id DESC
LIMIT 2;
```

결과는 다음과 같다.

```text
C — 좋아요 80개
A — 좋아요 75개
```

**이미 봤던 A가 다시 나온다.**

쿼리가 기억하는 것은 마지막 조회의 경계인 `(90, 104)`다.

“A는 이미 보여줬으니 제외하자”라는 정보는 들어 있지 않다.

그사이에 A의 좋아요 수가 줄면서 조회 조건에 다시 포함된 것이다.

ID를 함께 사용했는데도 이런 일이 생긴다.

ID는 좋아요 수가 같은 글들의 순서를 정해준다. **좋아요 수 자체가 바뀌는 것까지 막아주지는 않는다.**

반대 상황도 생각할 수 있다.

처음 상태에서 아직 보지 않은 C의 좋아요가 80개에서 110개로 늘었다면, C는 커서 앞쪽으로 올라간다.

그러면 좋아요 90개 뒤쪽을 계속 조회하는 동안에는 C를 만나지 못할 수 있다. 목록을 처음부터 다시 불러오면 그때 보게 된다.

## 읽었다는 표시와 순위는 별개다

여기서 읽은 글을 회색으로 표시하는 화면을 다시 생각해보면 이해하기 쉽다.

회색 표시는 “이 글을 읽었다”는 정보다.

인기순은 “지금 이 글을 어디에 놓을 것인가”에 관한 기준이다.

이미 읽은 글이라고 좋아요 수가 멈추는 것은 아니다. 다른 사람들이 반응하면 위치는 계속 바뀔 수 있다.

그래서 읽음 표시가 있는 글이 다른 위치에서 다시 보인다고 해서, 곧바로 잘못된 동작이라고 생각할 필요는 없다.

물론 **새로고침 후 순서가 바뀌는 것**과 **이어서 불러온 목록에 같은 글이 다시 나오는 것**은 구분해야 한다.

앞의 쿼리 예시는 그중에서도 정렬값이 바뀌면서 글이 커서의 앞뒤를 이동하는 경우다. 실제 서비스에서 보이는 모든 중복이 이 원인이라는 뜻은 아니다.

## 인기순이라면 자연스러운 결과일 수도 있다

인기글을 보는 사용자는 지금 반응이 많은 글을 보고 싶을 수 있다.

그렇다면 순위가 계속 바뀌는 것도 이해할 수 있다.

반면 아래로 계속 내려가는 동안에는 아직 보지 않은 글만 만나고 싶을 수도 있다.

서비스는 이런 기대에 따라 이미 본 글을 제외하거나, 탐색하는 동안 같은 순위를 유지하거나, 새로고침할 때 새로운 순위를 보여주는 방식을 선택할 수 있다.

다만 이미 본 글을 제외하는 것만으로, 커서 앞으로 올라간 글까지 다시 찾아주는 것은 아니다.

결국 커서 페이징을 썼다는 사실만으로 모든 상황이 정리되지는 않는다.

**최신순에서 이어 읽던 기준은 거의 움직이지 않았지만, 인기순의 기준은 내가 화면을 보는 동안에도 바뀔 수 있다.**

다음에 인기글 목록에서 회색으로 표시된 글을 다시 만나면, 단순히 “왜 또 나오지?”에서 한 번 더 생각해볼 수 있을 것 같다.

“내가 목록을 내려오는 동안, 이 글의 위치도 움직였을 수 있겠네.”
