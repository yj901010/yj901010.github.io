AWS에서 AI로 Aurora MySQL의 데드락을 분석하는 글을 봤다.

테스트 상황은 이랬다. 두 트랜잭션이 같은 두 테이블을 서로 반대 순서로 수정한다.

```text
트랜잭션 1: A의 락을 가진 상태에서 B를 기다림
트랜잭션 2: B의 락을 가진 상태에서 A를 기다림
```

서로 상대가 가진 락을 기다리니까 진행되지 않는다. MySQL은 이 데드락을 감지하면 한쪽 트랜잭션을 롤백한다.

작성자는 Kiro에 MCP를 연결하고 이 상황을 분석해달라고 했다. AI는 `SHOW ENGINE INNODB STATUS` 같은 진단 정보를 조회해서, 서로 다른 테이블 접근 순서 등을 원인으로 설명했다.

그리고 접근 순서를 통일하고, 트랜잭션을 짧게 유지하라는 제안을 했다. 추가로 오래 걸리는 쿼리를 확인할 수 있도록 슬로우 쿼리 로그도 켜라고 했다.

그때 제시한 명령이 이거였다.

```sql
SET GLOBAL slow_query_log = 'ON';
```

여기까지만 읽으면 그냥 실행해도 될 것 같다. 실제 DB까지 보고 알려준 답변이니까.

그런데 원문 뒤쪽에서 이 명령을 다시 짚는다.

Aurora의 마스터 사용자에게는 필요한 권한이 없어서, 이 명령은 `ERROR 1227`로 실패한다고 한다. Aurora에서는 DB 파라미터 그룹으로 설정해야 한다는 거다. [AWS 원문](https://aws.amazon.com/blogs/database/analyzing-aurora-mysql-issues-with-kiro-ide-and-aurora-mysql-mcp-server/)

“데드락 분석은 해줬는데, 같이 알려준 설정 방법은 안 맞았네?”

로그를 켜서 더 살펴보자는 취지는 이해가 된다. 다만 그걸 켜는 방법이 Aurora 환경에 맞지 않았던 것이다.

그러면 어떻게 해야 할까?

Aurora에 연결된 사용자 지정 파라미터 그룹에서 로그 관련 값을 설정하면 된다. 예를 들어 아래처럼 설정할 수 있다. SQL로 실행하는 명령이 아니라 파라미터 그룹에 넣는 값이다.

```text
slow_query_log = 1
long_query_time = 2
log_output = FILE
```

슬로우 쿼리 로그를 켜고, 실행 시간이 2초를 넘는 쿼리를 기록하도록 기준을 잡고, 파일로 남기는 설정이다. 2초는 예시이므로 서비스에 맞게 정하면 된다. [Aurora 로그 설정 문서](https://docs.aws.amazon.com/en_en/AmazonRDS/latest/AuroraUserGuide/USER_LogAccess.MySQL.LogFileSize.html)

설정을 적용한 뒤에는 실제 값이 반영됐는지, 로그도 남는지 확인하면 된다.

물론 로그를 켠다고 앞의 데드락이 해결되지는 않는다. 해당 상황에서는 테이블 접근 순서를 맞추는 등의 수정이 필요하고, 슬로우 쿼리 로그는 이후 오래 걸리는 쿼리를 살펴보기 위한 추가 제안이었다.

나는 이 부분에서 한 번 멈춰서 보게 됐다.

실제 DB를 조회한 답변이면 해결 방법도 그 환경에 맞춰 나왔을 거라고 생각하기 쉽다. 그런데 분석이 도움이 됐어도, 뒤에 붙은 명령까지 모두 맞는 건 아니었다.

AI가 알려준 원인은 실제 로그와 맞는지 보고, 제안한 명령은 공식 문서와 비교하고, 적용한 뒤에는 결과도 확인해야겠다.

“DB까지 보고 알려줬으니까 맞겠지” 하고 바로 복사하기에는, 한 번 더 볼 부분이 있었던 것 같다.
