Spring Batch 릴리스 글을 보다가 좀 이상한 숫자를 봤다.

파티션은 837개인데, 메모리에 올라온 `StepExecution` 객체는 700,569개였다고 한다.

“흠.. 837개를 나눠서 돌렸는데 왜 70만 개나 생기지?”

처음에는 작업하면서 뭔가 많이 쌓인 건가 싶었다. 그런데 읽어보니 워커가 끝났는지 확인하는 과정에서 생긴 문제였다.

2026년 10월 22일 올라온 [Spring Batch 공식 글](https://spring.io/blog/2026/10/22/spring-batch-6/)에서 소개한 `6.1.0-RC1`의 개선 내용이다. 직접 겪은 사례는 아닌데, 어떻게 이런 숫자가 나왔는지 한번 따라가보면 좋을 것 같았다.

배치 작업을 여러 파티션으로 나눠서 맡겼다고 해보자.

일을 나눠줬으면 이제 다 끝났는지도 확인해야 한다. 아직 누군가는 처리 중일 수 있으니까.

공식 글에서 다룬 `MessageChannelPartitionHandler`는 Job Repository를 주기적으로 조회해서 워커의 완료 여부를 확인한다. 여기까지는 자연스럽다.

그런데 이때 가져오는 게 생각보다 많았다.

워커 하나의 `StepExecution`을 읽으면, 그 실행이 속한 `JobExecution`과 그 안의 전체 `StepExecution`까지 같이 가져왔다고 한다.

“잠깐, 하나 끝났는지 보려는데 다른 실행 정보도 다 가져온다고?”

파티션이 3개라고 생각하면 조금 편하다. 아래는 실제 코드를 옮긴 건 아니고, 중복해서 가져오는 흐름만 줄여본 예시다.

```text
파티션 A의 실행 조회
  → JobExecution
    → 전체 실행 정보 [A, B, C]

파티션 B의 실행 조회
  → JobExecution
    → 전체 실행 정보 [A, B, C]

파티션 C의 실행 조회
  → JobExecution
    → 전체 실행 정보 [A, B, C]
```

A를 확인할 때 A, B, C를 가져오고, B를 확인할 때도 A, B, C를 가져온다. C도 마찬가지다.

같은 실행 기록을 나타내는 객체가 계속 중복해서 생기는 것이다.

이걸 공식 글의 837개에 대입하면 처음 봤던 숫자가 나온다.

```text
837 × 837 = 700,569
```

해당 사례에서는 폴링하는 노드가 메모리를 15GB 사용했다고 한다. 같은 양의 작업을 하던 다른 노드는 1.5GB였다.

이 정도면 “끝났나?” 하고 확인하는 쪽도 한번 봐야 하지 않을까 싶다. 배치가 메모리를 많이 쓴다고 하면 데이터를 읽고 처리하는 부분부터 생각할 것 같은데, 이런 데서도 차이가 날 수 있었던 거다.

그러면 매번 전체 실행 정보를 가져와야 했을까?

기다릴지 말지만 정하려는 거라면, 아직 실행 중인 워커가 몇 개 남았는지만 알아도 되지 않을까?

개선된 방식에서는 다음 메서드로 그 수를 확인한다.

```text
JobRepository#countRunningStepExecutions(Collection<Long>)
```

폴링할 때는 실행 중인 워커 수를 확인하고, 전부 끝나면 `JobExecution`을 한 번 가져오는 식이다.

공식 글에서는 같은 사례의 `StepExecution` 객체 수가 700,569개에서 837개로 줄었다고 설명한다. 다만 이 수를 세는 기능을 지원하지 않는 저장소 구현에서는 기존 방식으로 동작한다. [Spring 공식 설명](https://spring.io/blog/2026/10/22/spring-batch-6/)

여기서 “실행 중인 게 없으면 전부 성공한 건가?” 싶을 수도 있는데, 그건 따로 봐야 한다. 실패해서 끝난 작업도 있을 수 있으니까. 더 기다려야 하는지와 어떤 결과로 끝났는지는 다른 이야기다.

그리고 객체 수가 837분의 1이 됐다는 거지, 배치 전체가 837배 빨라졌다는 뜻은 아니다. 소개된 사례에서 실행 객체가 얼마나 줄었는지를 보여주는 숫자로 보면 될 것 같다.

읽고 나니 평소 작성하는 조회 코드도 좀 생각났다.

예를 들어 데이터가 있는지만 확인하려고 목록을 가져온 다음 `isEmpty()`를 호출하거나, 개수만 필요한데 전부 조회해서 `size()`를 보는 경우다.

이미 목록 조회 메서드가 있으면 그냥 가져다 쓰고 싶기도 하다. 데이터도 몇 개 없으면 굳이 따로 만들어야 하나 싶고.

그런데 그게 반복문 안에 들어가고, 주기적으로 계속 실행되면 얘기가 달라질 수 있겠다.

이번 사례도 처음에는 “파티션이 많으면 객체도 좀 많아질 수 있지 않나?” 싶었다. 그런데 하나씩 따라가보니 같은 실행 정보를 반복해서 가져오는 부분이 있었다.

나중에 배치 메모리 문제를 보게 된다면, 데이터를 처리하는 코드와 함께 상태를 확인하는 코드도 한번 봐야겠다.

“이거 끝났는지만 알면 되는데, 굳이 전부 가져오고 있는 건 아닐까?”
